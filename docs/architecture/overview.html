Cardputer ADV Recorder + Sync

How the voice recorder firmware and the desktop sync app are built, how they talk to each other, and what has been implemented so far (architecture milestones 1 to 5). The architecture PDF in this folder is the original design; this page describes the code as it is.

1. Overview

The project is two programs and one dev tool in one repository. They share nothing but wire protocols, so each builds and tests on its own.

firmware/

Recorder for the M5Stack Cardputer ADV (ESP32-S3, no PSRAM). Records 16 kHz mono 16-bit WAV to microSD; pairs over Bluetooth LE; serves recordings over HTTPS with mutual TLS. C++, PlatformIO, Arduino. Fork of Moskic/cardputer-adv-recorder v1.4.0.

desktop/

Tauri 2 app: Rust core (BLE, TLS, mDNS, SQLite, keychain, sync engine) and a React UI. Local accounts, pairing wizard, library with playback, background auto-sync from the system tray.

tools/mock-device/

Rust fake device that serves the /v1 protocol over plain HTTP from a folder of WAVs, with fault injection and mDNS, so the desktop can be developed without hardware.

Feature summary. Stable recording ids embedded in each WAV; a sync index on the SD card; numeric-comparison Bluetooth pairing with WiFi provisioning; HTTPS sync with keys pinned on both sides; resumable, hash-verified downloads with an ack-last rule; optional delete-after-sync that never touches locked files; device discovery over mDNS; auto-sync when the device is plugged in; desktop tray worker, stay logged in and start at login. No cloud.

2. How it works for the user

  1. Record. R records; Enter/Esc/R stops and saves. Each new file gets a random 128-bit id inside the WAV, so renames and reused names never confuse sync.
  2. Pair once. On the device: hold G0 > Sync > Pair with Desktop. In the app: Devices > Pair new device. Both screens show the same six-digit code; press Enter on the Cardputer and click Codes match. Pick the WiFi network from the list the device scanned and type the password; the device tests it once.
  3. Sync. Press S in the library, or plug the device into USB with Auto-Sync Charging on. The device joins WiFi, starts its HTTPS server and announces itself. The desktop app (running in the tray, window closed is fine) finds it and pulls every new recording, then tells it to stop.
  4. Library. Recordings appear grouped by device and day. Play in the app, search, rename (on the desktop only), show the file in Explorer/Finder, or delete the copy on the device.

3. System architecture

Two radios, two jobs: Bluetooth LE carries small, rare control traffic (pairing and WiFi settings); WiFi carries audio. The device is the server and the desktop pulls, so the desktop only makes outbound connections (no firewall prompt).

Highlighted path moves audio. Bluetooth is only on in pairing mode; WiFi only in sync mode or while pairing tests the network.

4. Firmware

Structure

RecorderApp is one class that owns every service and a State enum driven from update() on the Arduino loop. Its methods are split across files by concern (src/app/*.cpp), and hardware sits behind small services (src/hardware/). New sync code lives in new files with small hooks into RecorderApp, so the fork stays easy to rebase on upstream.

FolderContents
src/app/recording_flow, capture_pipeline, playback_flow, file_browser, recorder_settings, recorder_ui, screen_saver, sync_flow, pairing_flow
src/hardware/board, audio, power, storage, wifi (station + scan + mDNS), ble (NimBLE GATT)
src/media/wav_format (pure), wav_file (reader/writer), recording_chunk (pure), file_naming
src/sync/sha256, sync_index, protocol, cbor, pairing_math (pure, host-tested); device_identity, peer_store, secure_channel, sync_server (mbedtls / esp_https_server)

States

Radios are on only in kSyncing and kPairing. Both return to the library or settings; recording and playback never run with a radio on.

Recording pipeline

Recording streams through ten static 4096-sample buffers (80 KB) and a dedicated FreeRTOS writer task with free/ready queues, so length is limited by SD space, not RAM. The WAV header is written up front with placeholder sizes and rewritten on save. The save step checks that the file on disk is exactly header + audio bytes (92 + data for new files, 44 + data for old ones). In sync mode, audio is idle, so the HTTPS server reuses the same 80 KB as its SD read buffer instead of allocating.

5. Recording identity (milestone 1)

File names are not stable (they can be renamed, or reused after a delete), so every new recording carries a cprc RIFF chunk between fmt and data. Players that do not know the chunk skip it.

RIFF12 B
fmt24 B
cprc hdr8 B
version1 B (=1)
reserved3 B
recording id16 B random
device id8 B
start timeint64 ms, 0 = unknown
reserved4 B
data hdr8 B
audioPCM

The header is 92 bytes. The reader parses it sequentially without seeking (seeks are unreliable on some cards) and still falls back to walking chunks. Files from older firmware get an id derived from SHA-256(NAME|size|SD timestamp); a copied file whose id collides gets a derived id too.

Sync index: /RECORDER.SYN

CPREC-SYN 1<TAB><cursor>
<id> <name> <size> <created_ms> <duration_ms> <changed> <sha256> <acked_by>   (tab-separated, one line per recording)
  • The cursor increases on every add, rename, delete and ack; each entry remembers the cursor of its last change, so manifest?since=N returns only what changed. Caching a hash is not a visible change.
  • Hooks in save, delete and rename keep it current; at sync start a reconcile pass drops entries for missing or resized files and indexes files copied onto the card from a computer.
  • It is written to /RECORDER.SYT and renamed, and the loader falls back to the temp file, so a crash mid-save loses nothing. Damaged lines are skipped, not fatal.

6. Bluetooth pairing (milestone 4)

Pairing is done at the app level, not with OS Bluetooth bonding, because bonding behaves differently on Windows, macOS and Linux. The GATT service has two characteristics: Info (read: id, firmware, paired) and Control (write + notify). The device advertises only while Settings > Sync > Pair is open, for at most two minutes; its scan response carries "CP", flags and the device id.

Exchange

For an already-paired desktop (known), the device answers session instead of waiting for a code, and the desktop may send set_wifi (Change WiFi).

Why a commitment

If both sides simply swapped keys and nonces, a man-in-the-middle could pick its own nonce after seeing the device's, trying a million values until the two six-digit codes match. The desktop therefore commits to its nonce first and reveals it after seeing the device's, the same defence as Bluetooth LE Secure Connections. Each side's code is fixed before the attacker can influence it, so a forged pairing shows mismatched codes with probability 999,999 in a million.

Framing and encryption

LayerFormat
Fragmentbyte 0 = 1 on the last fragment, 0 otherwise; messages up to 2048 bytes. Notifications use MTU − 3; desktop writes ≤ 180 bytes.
Message0x00 + CBOR (plain) or 0x01 + counter (8 B, big endian) + AES-256-GCM ciphertext + tag; the 9-byte header is the AAD.
Noncedirection ('H' or 'D'), three zero bytes, counter. Counters must increase, so replays are dropped.
PayloadCBOR map with text keys; t is the type. The firmware has its own small CBOR encoder/decoder that produces the same bytes as the desktop's ciborium.

Rules from the design: one owner per device; a new owner needs the code and a physical Enter; replacing an owner clears the old owner's acks; Forget Pairing wipes peer, WiFi and acks; removing a device in the app forgets it on the desktop only.

7. Sync protocol (/v1)

Plain HTTP/1.1 semantics with JSON bodies, carried over HTTPS with mutual TLS on port 8443. The desktop pulls; every step is idempotent, so a dropped connection simply restarts from the manifest and resumes partial files with Range.

RequestResponseNotes
GET /v1/infodevice_id, firmware, battery_pct, free_bytes, unsynced, clock_setFirst call; proves the pinned identity
POST /v1/time{}Body {unix_ms, tz_offset_min}; sets the device clock (SNTP is the fallback)
GET /v1/manifest?since=N{cursor, recordings:[{id, name, size, created_ms, duration_ms, locked, acked}]}Only entries changed after N; streamed entry by entry
GET /v1/recordings/{id}WAV bytes, 200 or 206Range supported; 32 KB SD reads; hashed while streaming a whole file
GET /v1/recordings/{id}/sha256{sha256}Cached, or computed (about 20 s for 19 MB)
POST /v1/recordings/{id}/ack{acked, deleted}Body {sha256}; must match. Deletes only if Delete After Sync is on and the file is not locked
DELETE /v1/recordings/{id}{deleted}Only on explicit request from the app; refuses locked files
POST /v1/done204Device stops the server and WiFi, returns to the library

Errors are {code, message} with 4xx/5xx: not_found, sd_error, hash_mismatch, busy, low_battery, locked, bad_range, bad_request.

Desktop algorithm, per sync

  1. info (and check it is the expected device id), then time.
  2. manifest?since= the cursor stored for this device.
  3. For each recording not in the library: download to <library>/.partial/<id>.wav.part, resuming from its size (up to 5 attempts while the connection keeps dropping).
  4. Hash locally, fetch the device's hash, compare; on mismatch delete the partial and retry once.
  5. Rename into <library>/<device>/<YYYY-MM-DD>/<name>__<id8>.wav, write the SQLite row, then ack. A crash between those steps never leaves the device believing a file is safe; the next sync finds the unacked row and re-acks it from the library.
  6. Same id with a new name: update the display name only. Items gone from the device stay in the library.
  7. Store the new cursor only if every entry succeeded (so failures are listed again), then done.

8. Hands-free sync (milestone 5)

Device: announce

While the HTTPS server runs, the device announces _cprec._tcp.local with TXT id=<device id>. Sync mode ends after a desktop calls done, or after 3 minutes (automatic start) / 10 minutes (S) with no request.

Device: auto-sync when charging

In the library, idle for 15 s, paired, with unsynced recordings and on external power: start sync mode by itself. 10-minute cooldown after any attempt; Esc pauses it until unplugged.

Desktop: discovery worker

mdns-sd browses for the service. Each device is synced once per appearance; a failed sync is retried after 60 s while it keeps announcing. The discovered address replaces the stored one.

Desktop: tray

Closing the window keeps the app in the tray while a user is logged in with auto-sync on. Tray menu: Open, Sync devices on the network, Quit. Start at login launches hidden.

Charging is a heuristic. The Cardputer ADV has no charge-status signal, so "external power" means a computer is sending USB frames to the serial port, or the battery is at charging voltage (4.15 V or more). A wall charger may only count once the battery is nearly full.

11. Security model

ThreatMitigation
Someone nearby reads data over BluetoothBefore pairing only Info is readable; everything after the exchange is AES-GCM with the session key; BLE is on only in pairing mode (2 minutes max)
Man-in-the-middle during pairingNumeric comparison over a transcript with a committed nonce; physical Enter on the device
Someone on the LAN pulls or deletes filesMutual TLS: the device accepts only the paired desktop's certificate
Fake device feeds files to the desktopThe desktop accepts only the device key it paired with, so a spoofed mDNS record fails the handshake
Silent re-pairing by a strangerCode plus Enter on the device; pairing mode times out
Another desktop user sees my recordingsPer-user accounts, libraries, devices and host keys; the worker syncs only the logged-in user's devices. "Stay logged in" is off by default and meant for single-user computers
Lost Cardputer / stolen laptopNVS and the SD card are not encrypted (flash encryption would complicate USB reflashing); library files are plain WAV. Host keys are in the OS keychain

Unpaired dev devices (the mock) use plain HTTP and are clearly marked "dev · HTTP" in the app; paired devices always use HTTPS.

12. Testing

Flashing is slow, so most behaviour is verified on the PC. Pure firmware logic compiles for the host; the desktop is tested against fakes and local servers; the mock device stands in for hardware.

SuiteCountCovers
Firmware test_wav9WAV header encode/parse, chunk walking, naming (upstream)
Firmware test_sync17cprc header round trip and old-reader compatibility, SHA-256 vectors, sync index (cursor, reconcile, parse), routes, Range, JSON
Firmware test_pairing8HMAC (RFC 4231), HKDF (RFC 5869), CBOR, framing, and the vectors shared with the desktop
Desktop Rust39 (+1 keychain)Sync engine vs FakeDevice (resume, bad hash, rename, re-ack, delete-after-sync, busy, wrong device); pairing vs a Rust reference device (new, known, cancelled, tampered); mutual TLS vs a local TLS 1.2 server (paired, impostor device, stranger host); discovery rules; DB migrations; accounts

End-to-end runs against the mock device: full sync with delete-after-sync and a locked file; incremental re-sync; every fault mode (dropped connection with resume, hash mismatch, busy, low battery); and hands-free: the real app started hidden in the tray with a remembered user, discovered the mock over mDNS, corrected its address and synced both recordings within 5 seconds.

Shared vectors keep both pairing implementations honest: for fixed inputs both produce commitment e13cafbb…, session key 4a51c523…, code 581958 and identical CBOR bytes.

Deviations from the architecture PDF

  • Pairing adds a nonce commitment (hello / hello / reveal), against code grinding.
  • Bluetooth stays off during sync (no Status characteristic, no BLE discovery), to leave heap for WiFi and TLS; discovery is mDNS only.
  • Unpaired dev devices are supported over plain HTTP for the mock.
  • M5GFX is pinned to 0.2.27 because upstream's 0.2.22 is no longer in the PlatformIO registry.

Risks to check on hardware

  • Heap on a chip without PSRAM: 80 KB audio buffers plus WiFi and a TLS session, with the Bluetooth controller memory reserved (the Arduino core would otherwise free it at boot). Static RAM is 43% of 320 KB; serial logs print free and minimum heap during pairing and sync.
  • Throughput over TLS from the 10 MHz SD bus (logged as KB/s per file).
  • Charging detection with wall chargers (voltage heuristic).
  • Coexistence of WiFi and BLE while pairing tests the network.
